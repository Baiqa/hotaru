# План: Этап 1 → «Эмбеддинги заголовка+лида + pgvector-индекс»

Дата: 2026-09-27. Вторая подзадача Этапа 1 (после "Сущностей"), не весь этап целиком.
Решения этой сессии: провайдер эмбеддингов — Google Gemini Embedding API (модель
gemini-embedding-2, рекомендована Google для новых проектов, мультиязычная,
100+ языков). Ключ `GOOGLE_API_KEY` уже добавлен пользователем в worker/.env напрямую
(не через чат).

Решение по OpenRouter пересмотрено: убрали его из проекта совсем (ключ удалён из
worker/.env и .env.example). У Google Gemini есть бесплатный тир и для чат-моделей
(Flash/Flash-Lite) — LLM для серой зоны кластеризации (следующая подзадача после этой)
тоже будет на Gemini, один провайдер вместо двух. Точную модель для той задачи не
фиксируем сейчас — источники по актуальным free-tier моделям на 2026 год расходятся
(мелькали 2.5 Flash-Lite, 3.1 Flash-Lite и др.), проверим по официальной документации
Google, когда дойдём до той подзадачи.

Проверено перед планом: расширение `vector` в Supabase ещё не включено (доступна
версия 0.8.2, `installed_version: None`) — миграция должна его включить.

## 1. Миграция БД
- `create extension if not exists vector;`
- `articles.embedding vector(768)` — nullable. 768 — один из рекомендуемых Google
  вариантов output_dimensionality (128/768/1536/3072), компактный, gemini-embedding-2
  сам нормализует усечённые эмбеддинги (в отличие от gemini-embedding-001, где для
  этого нужна ручная нормализация).
- HNSW-индекс на косинусную близость: `create index articles_embedding_hnsw_idx
  on articles using hnsw (embedding vector_cosine_ops);` — нужен и для раздела 3.3
  CLAUDE.md ("косинус эмбеддингов" как сигнал), и для будущего отбора кандидатов
  ("топ-50 через pgvector") в следующих подзадачах.
- Отдельной колонки-флага вроде `embedded_at` не заводим — "обработано" здесь
  ровно то же самое, что "embedding not null", лишнее поле не нужно.

## 2. Зависимость воркера
- `google-genai` (актуальный SDK; `google-generativeai` — устаревший, не он)

## 3. Модуль `worker/src/hotaru_worker/embeddings.py`
- `embed_text(client, text: str) -> list[float]` — модель `gemini-embedding-2`,
  `output_dimensionality=768`
- Текст на эмбеддинг = `title` + `\n` + `lead` (lead может отсутствовать — тогда
  только title), по разделу 3.3 CLAUDE.md: "считать по заголовку и лиду, не по
  всему тексту"
- Обработка rate-limit (429): retry с backoff. Точные цифры free tier Google не
  публикует в открытой документации (видны только в самом AI Studio под ключом
  пользователя) — закладываемся на осторожный retry, а не на конкретное число.

## 4. Точка входа `hotaru-embed-articles`
По образцу `hotaru-extract-entities`: батчи, новое соединение с БД на каждый батч
(урок из прошлой подзадачи — пул Supabase рвал долгие соединения), пропуск уже
обработанных статей (`where embedding is null`).

## 5. Проверка перед «готово»
- Прогон на всех 548 статьях — векторы реально заполнились (768 чисел)
- HNSW-индекс строится без ошибок
- Идемпотентность: повторный прогон не делает новых вызовов API (0 обработано)
- Смысловая проверка: беру пару статей на близкую тему и пару на разные темы,
  сравниваю косинусную близость через SQL (`1 - (a.embedding <=> b.embedding)`) —
  близкие темы должны давать заметно более высокое сходство, чем случайные пары
- Rate-limit обрабатывается по коду (не обязательно живой тест — спровоцировать
  429 специально может быть дорого/долго)

## Вне скоупа этой подзадачи (следующие подзадачи Этапа 1)
Функция скоринга (4 сигнала), отбор кандидатов через pgvector, LLM для серой зоны
(Gemini, конкретная модель — по месту), таблицы `events`/`event_articles`, фоновые
merge/split. B-Cubed-разметка — когда появятся `events`.
