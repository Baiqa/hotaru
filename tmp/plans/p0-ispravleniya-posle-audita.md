# План P0: исправления после аудита

Составлен 2026-11-12 по итогам аудита от 2026-11-11. Код не меняется, пока план не одобрен.
Каждая фаза — отдельная задача и отдельный коммит (CLAUDE.md §7), со своим критерием готовности.

## Решения пользователя (2026-11-11/12)

| Вопрос | Решение |
|---|---|
| Бюджет LLM | Пока только бесплатные тарифы. Платный — когда все функции заработают |
| Habr | Оставить в источниках |
| Планировщик | Один workflow на GitHub Actions |
| Одиночные события | Тоже должны получать свой текст. Цель продукта: пользователь читает всё на сайте и не уходит к источникам |
| Порядок при нехватке квоты | Сначала события с 2+ изданиями, одиночные — на остаток, от свежих к старым. Старше 3 суток без текста — не обрабатывать |
| Фотографии | В P0 не делаем, отдельная задача позже |
| Накопленные данные | Пересобрать события за последние 7 дней. Более старое скрыть с главной и не обрабатывать |

## Что получится в итоге

- Полный текст чужих статей недоступен снаружи.
- Конвейер запускается без взаимных отмен, каждый шаг оставляет запись о запуске.
- Квота LLM тратится сначала на свежие события с несколькими изданиями.
- Даты статей точные, сущности не дублируются по падежам, служебные «МОСКВА … РИА Новости» не считаются сущностями.
- Главная показывает свежие и важные события с честными цифрами.
- БД не упирается в лимит бесплатного плана.

## Порядок фаз

1. Закрыть полный текст (безопасность)
2. Единый workflow и журнал запусков
3. Даты публикации
4. Сущности и скоринг
5. Бюджет LLM: очереди, приоритеты, пакетные запросы
6. Пересборка событий за 7 дней
7. Фронт: честные цифры и порядок на главной
8. Размер БД
9. Мониторинг и оповещения

Фазы 1, 2, 7 (часть про подписи) и 8 (удаление индекса) независимы и дают эффект сразу.
Фаза 6 запускается только после 3, 4 и 5.

## Фаза 1. Закрыть полный текст

**Статус: выполнена 2026-11-12.** Миграция `restrict_public_columns` применена к БД.
Проверено: 7 запретных запросов анонима дают 42501, 7 запросов фронта дают 200; страницы всех типов
отдают 200 локально и на Vercel; цитаты в новом коде не длиннее 300 символов; воркер читает и пишет.
Осталось вне фазы: 56 старых цитат длиннее 300 символов по-прежнему лежат в `claims.evidence`
и читаются через API напрямую (на сайте обрезаются).

**Проблема.** Публичный ключ читает `articles.body` (проверено: 8109 символов, по 1000 строк на запрос).

**Что делаем**

- Миграция: `revoke select on public.articles from anon, authenticated`, затем
  `grant select (id, source_id, url, canonical_url, title, lead, published_at, fetch_status, created_at)`.
  Политика RLS остаётся. Воркер ходит под ролью `postgres`, его это не затрагивает.
- То же для `claims.embedding`: оставить анониму `id, article_id, text, type, evidence, created_at`.
- [claim_extraction.py](../../worker/src/hotaru_worker/claim_extraction.py): отбрасывать факт, если `evidence` длиннее 300 символов
  (правило «цитата не длиннее одного предложения»). В промпт добавить это требование явно.
- Фронт: на случай старых длинных цитат обрезать показ `evidence` до 300 символов.

**Готово, когда**

- Запрос `articles?select=body` с публичным ключом возвращает ошибку прав доступа.
- Главная, событие, сравнение, сюжет и статья отдают 200 локально и на Vercel.
- Запуск `hotaru-collect` и `hotaru-extract-claims` проходит без ошибок прав.

**Риск.** Фронт нигде не делает `select *` по `articles` (проверено по коду), но это надо перепроверить сборкой и обходом страниц.

## Фаза 2. Единый workflow и журнал запусков

**Проблема.** Три workflow делят одну группу concurrency: новый ожидающий запуск вытесняет предыдущего.
За 3,2 суток `collect`: 5 успехов, 7 отмен, 2 падения.

**Что делаем**

- Новая таблица `pipeline_runs (id, step, started_at, finished_at, status, stats jsonb)`, без публичной политики.
- Новый модуль `runlog.py`: контекст `step("имя")` пишет старт, финиш, статус и статистику шага;
  функция `due("имя", часы)` отвечает, пора ли запускать редкий шаг.
- Один файл `.github/workflows/pipeline.yml` вместо четырёх: расписание `*/30`, одна группа, один job
  с таймаутом 120 минут, шаги идут последовательно. Порядок шагов:
  1. сбор, сущности, эмбеддинги статей, кластеризация, слияние, сюжеты;
  2. факты, эмбеддинги фактов, группировка и синтез для событий с 2+ изданиями;
  3. факты и синтез для остальных (одиночных);
  4. раз в сутки по `due()`: разделение событий, ряды World Bank, очистка (фаза 8);
  5. мониторинг — в каждом запуске.
- Суточные шаги привязаны к журналу в БД, а не ко второму cron: так их нельзя «вытеснить».
- Старые четыре файла удаляются после суток стабильной работы нового.

**Готово, когда**

- За 24 часа нет отменённых запусков, кроме таймаута job.
- В `pipeline_runs` есть запись по каждому шагу каждого запуска.
- Суточные шаги выполнились ровно один раз за сутки.

**Что это не решает.** Частоту запусков задаёт GitHub (сейчас раз в 2–4 часа). Часть статей РИА и ТАСС
между запусками может выпадать из окна RSS. Лечится только своим сервером с cron — это P1.

## Фаза 3. Даты публикации

**Проблема.** Дата из trafilatura (точность до дня) перекрывает точное время из RSS: у 3484 из 3484
полнотекстовых статей время 00:00 UTC, у 61 статьи дата ошибочна больше чем на 30 дней.

**Что делаем**

- [collect.py:46](../../worker/src/hotaru_worker/collect.py): сначала время из RSS, дата страницы — только если в RSS его нет.
- Проверка здравого смысла: дата из будущего или старше 7 суток до момента сбора заменяется временем сбора.
- Заголовок: сначала из RSS, со страницы — только если в RSS пусто (убирает хвост «| TechCrunch»).
- Разовая правка старых записей одной миграцией данных:
  если дата статьи в пределах 2 суток от `created_at` — поставить `least(created_at, конец этого дня)`;
  иначе — `created_at`. Точное время старых статей восстановить нельзя, это приближение.

**Готово, когда**

- У новых полнотекстовых статей время не полуночное (доля 00:00 меньше 5%).
- Нет статей с `published_at` позже `created_at` + 1 час и раньше `created_at` − 7 суток.
- Тесты pytest на выбор даты и заголовка (первые тесты в проекте, каталог `worker/tests`).

## Фаза 4. Сущности и скоринг

**Проблема.** «Трамп», «Трампа», «Трампом», «Трампу» — разные сущности. «Москва» (1137 статей РИА)
и «Риа Новости» (1540) берутся из служебной строки в теле статьи вида
`МОСКВА, 9 ноя - РИА Новости.` (проверено по текстам). Из-за этого у крупнейшего источника фильтр
«общая сущность» ничего не отсекает, а серая зона занимает 87% статей.

**Что делаем**

- [entities.py](../../worker/src/hotaru_worker/entities.py), до NER: вырезать служебные строки
  (`ГОРОД, дата - РИА Новости.`, `Москва. дата. INTERFAX.RU -`) и не заводить сущности
  с названием самого издания (небольшой стоп-список: «РИА Новости», «ТАСС», «Интерфакс», «INTERFAX.RU»
  и так далее — хранится рядом с `sources.yaml`).
- Фамилии в косвенных падежах. Проверено на установленных библиотеках:
  spaCy верно даёт падеж и род («Трампа» — Gen/Masc, «Захарова» — Nom/Fem),
  pymorphy3 имеет разбор-фамилию для «Трампа», «Путиным», «Токаева», «Лаврова», «Зеленского».
  Правило: если spaCy говорит «не именительный» — взять разбор pymorphy с граммемой `Surn`
  и тем же родом, привести к именительному. Если такого разбора нет («Мерца», «Макрона») —
  отрезать падежное окончание только тогда, когда получившаяся основа уже есть среди имён людей.
  Именительный падеж не трогаем («Токаев» остаётся «Токаев»).
- [scoring.py](../../worker/src/hotaru_worker/scoring.py): Жаккар сущностей с весами IDF (редкая общая сущность весит больше частой).
  Частоты считаются одним запросом на прогон.
- [clustering.py](../../worker/src/hotaru_worker/clustering.py): жёсткий лимит события из §3.3 — не присоединять статью, если
  от начала события прошло больше 72 часов или в нём уже 40 статей. Этого пункта не было в P0 аудита;
  добавлен, потому что без него пересборка (фаза 6) заново склеит цепочки вроде «Белгород, 79 статей».
- `gray_zone_verdicts`: добавить колонки со скором и четырьмя сигналами — пригодится для подбора порогов (P1).

**Как проверяем без траты квоты**

- Перезапускаем извлечение сущностей на 250 размеченных статьях (`worker/eval/labels.json`).
- Для всех пар из разметки считаем скор старым и новым способом и сравниваем ROC-AUC
  («одно событие» против «разные»). LLM не нужна.

**Готово, когда**

- AUC нового скора на размеченных парах не ниже старого.
- На окне 7 дней формы «Трамп*» на русском сведены в одну сущность, «Москва» (org) и «Риа Новости»
  не входят в топ-10 сущностей.
- Тесты pytest: нормализация фамилий (включая «Захарова» и «Токаев»), вырезание служебных строк, IDF-Жаккар.

**Риск.** Однословные фамилии неоднозначны («Захарова» — она или «у Захарова»). Правило опирается на
падеж и род от spaCy; на малой модели возможны ошибки. Проверяется тестами и выборочным просмотром.

## Фаза 5. Бюджет LLM

**Проблема.** Спрос около 2500–3000 вызовов в сутки против ~500 у Gemini и ~450–570 у Groq.
Очередь синтеза идёт от старых событий к новым и не помечает неудачи: в её голове события 2022–2023
годов и сентябрьские, 83 из 92 готовых сводок — у одиночных событий, у топ-30 главной сводок нет.

**5.1. Денормализованные поля события.** Миграция: `events.last_article_at`, `events.source_count`
(число изданий), `events.render_attempts`, `events.render_failed_at`. Одна функция
`refresh_event_stats(event_id)` вызывается при присоединении, создании, слиянии и разделении.

**5.2. Очередь синтеза** ([db.py:827](../../worker/src/hotaru_worker/db.py), [synthesize.py](../../worker/src/hotaru_worker/synthesize.py))

- Только формат `summary_30s`; `full_breakdown` выключаем, пока для него нет экрана.
- Порядок: `source_count >= 2` первыми, затем `last_article_at` по убыванию.
- Отсечка: события, у которых `last_article_at` старше 3 суток, в очередь не попадают.
- После неудачи растёт `render_attempts`; после трёх неудач событие откладывается на сутки.
- Перегенерация: если после создания сводки у события выросло число изданий.
- На вход модели идут группы фактов (одна строка на группу со списком изданий), не больше 40 строк.
  Сейчас уходят все сырые факты, до 267 на событие. У одиночных событий групп нет — туда идут
  сырые факты единственной статьи, с тем же потолком 40.
- В `renders.model` писать фактическую модель (сейчас константа).
- Защита от зацикливания: если за проход батча нет ни одной новой сводки — прогон завершается.

**5.3. Очереди фактов** ([extract_claims.py](../../worker/src/hotaru_worker/extract_claims.py), `embed_claims.py`, `group_claims.py`)

- Ключ `--scope multi|rest`: сначала статьи событий с 2+ изданиями, потом остальные от свежих к старым.
- Та же отсечка 3 суток и счётчик попыток на статье (`claims_attempts`), чтобы «отравленная» статья
  не блокировала очередь.
- Эмбеддинги и группировка фактов — только для событий с 2+ изданиями: внутри одиночного события
  группировать нечего. Сейчас на такие события приходится 2872 факта из 9523.

**5.4. Пакетные запросы серой зоны** ([cluster_events.py](../../worker/src/hotaru_worker/cluster_events.py), [gray_zone.py](../../worker/src/hotaru_worker/gray_zone.py))

- Перед обработкой батча статей считаем скоры без LLM, собираем пары серой зоны, которых нет в кеше,
  и отправляем по 10–20 пар одним запросом. Ответы кладём в кеш `gray_zone_verdicts`.
- Дальше работает существующий последовательный алгоритм, который теперь попадает в кеш.
  Логика решений не меняется, меняется только число запросов (лимит считается по запросам).
- Проверка качества до включения: прогнать 200 пар из кеша пакетами и сравнить с сохранёнными
  вердиктами. Порог: согласие не ниже 90% и ни одной замены `different` на `same`.
  Если не проходит — пакет уменьшаем или оставляем по одной паре.

**5.5. Эксперимент с пакетными эмбеддингами.** Квота эмбеддингов 1000 в сутки, а одних статей приходит ~800.
Неизвестно, считается ли запрос с несколькими текстами за один. Проверяем на практике в день,
когда квота полная. Если пакет считается за один запрос — переводим оба шага эмбеддингов на пакеты.
Если нет — статьи идут первыми, факты на остаток; локальная модель для фактов уходит в P1.

**Оценка расхода после изменений** (оценка, не измерение)

| Шаг | Было, вызовов в сутки | Станет |
|---|---|---|
| Серая зона | ~890 | ~80–100 |
| Синтез событий с 2+ изданиями | — | ~60–100 |
| Факты для событий с 2+ изданиями | — | ~150–250 |
| Одиночные: факты и синтез | ~1500 | на остаток квоты |

Одиночные события на бесплатной квоте получат текст не все. Все — после перехода на платный тариф;
тогда достаточно убрать отсечку и приоритеты менять не придётся.

**Готово, когда**

- Все свежие (моложе 3 суток) события с 2+ изданиями имеют сводку в течение двух запусков конвейера.
- В голове очереди синтеза нет событий старше 3 суток.
- Ни одно событие не генерируется больше трёх раз подряд без результата.
- Доля запросов серой зоны на статью упала минимум впятеро (по `pipeline_runs.stats`).
- Тесты pytest на пост-проверку синтеза и выбор очереди.

## Фаза 6. Пересборка событий за 7 дней

**Требует отдельного подтверждения перед запуском: это удаление данных.**

**Что затрагивает** (по состоянию на 11.11): 4470 статей в окне, 1232 события, 41 сводка.
Событий, смешивающих старые и новые статьи, нет — граница чистая.

**Шаги**

1. Резервная копия затрагиваемых таблиц в локальные файлы (COPY через psycopg):
   `events`, `event_articles`, `claim_groups`, `claim_group_members`, `renders`, `render_claims`,
   `stories`, `story_events`, `entities`, `entity_aliases`, `article_entities`.
2. Остановить расписание workflow на время пересборки.
3. Удалить события, в которых есть статьи окна (каскадом уйдут их группы фактов, сводки, связи с сюжетами).
   Статьи, тексты, извлечённые факты и кеш вердиктов серой зоны сохраняются.
4. Сбросить и заново извлечь сущности для статей окна и 250 размеченных статей; удалить осиротевшие сущности.
5. Кластеризация окна новым кодом (несколько запусков: квота серой зоны).
6. Сюжеты пересобрать целиком (LLM не нужна).
7. События старше окна (882) остаются в БД, ссылки на них работают, но на главной они не показываются
   и в очереди не попадают.
8. Включить расписание.

**Готово, когда**

- Нет активных событий без статей и статей окна без события (кроме ожидающих квоты).
- Нет событий больше 40 статей и длиннее 72 часов.
- Десять крупнейших событий просмотрены вручную: каждое про одно событие.
- В сюжетах нет ссылок на слитые события (сейчас 127).

**Последствия.** Ссылки на удалённые события окна перестанут работать (сайт не анонсирован, риск мал).
Пересборка займёт 1–2 суток квоты серой зоны.

## Фаза 7. Фронт: честные цифры и порядок

- `web/src/app/(list)/page.tsx`, `web/src/app/events/[id]/page.tsx`: вместо «19 источников» — «19 статей от 4 изданий».
- Главная: блок «Главное» (2+ изданий, последние 48 часов, по числу изданий и свежести, до 10)
  и «Свежее» (по `last_article_at`, 30). События старше 7 дней не показываются.
- Время на карточке — `last_article_at`, форматирование на клиенте в часовом поясе пользователя.
- На карточке — первое предложение сводки, если она есть.
- Страница одиночного события: сводка, если готова; иначе лид и ссылка на оригинал с пометкой «текст готовится».
- Сюжет: не показывать слитые события; склонение «событие / события / событий».

**Готово, когда:** сборка и линтер чистые; на живых данных подписи совпадают с подсчётом в БД
для пяти событий; время на странице совпадает с локальным.

## Фаза 8. Размер БД

- Удалить индекс `claims_embedding_hnsw_idx`: 22,4 МБ, 0 обращений, код его не использует.
- Суточный шаг очистки (**нужен ваш срок хранения, предлагаю 14 дней**): у статей старше срока
  обнулять `body`, у фактов событий старше срока — `embedding`. Заголовок, лид, факты и цитаты остаются.
  Это необратимо, поэтому включается только после подтверждения срока.
- В мониторинг: размер БД и прогноз до лимита плана.

**Готово, когда:** размер БД после очистки и `vacuum` меньше, чем до; рост за сутки записывается в журнал.

## Фаза 9. Мониторинг и оповещения

- Новые проверки по `pipeline_runs` и очередям: возраст самой старой необработанной статьи,
  время с последнего успешного сбора, доля статей без текста по источнику (ТАСС, Al Jazeera и NPR
  сейчас 100% и не ловятся), доля отклонённых генераций, размер БД.
- Критические проверки завершают шаг с ошибкой: job краснеет, GitHub присылает письмо владельцу.
  Некритические (серая зона) только пишутся в журнал, чтобы job не был красным постоянно.
- Сводка проверок выводится в итог запуска GitHub (step summary).

**Готово, когда:** искусственно созданная тревога (например, порог возраста очереди 0) делает job красным;
в обычном режиме job зелёный.

## Что не входит в P0

- Фотографии и статистика для событий (отдельная задача после P0).
- Тексты ТАСС, Al Jazeera, NPR: сначала выяснить причину отказа по каждому.
  Наблюдение из прогона 2026-11-12: страницы ТАСС отдают HTTP 200, текст отбрасывает сам trafilatura
  («discarding data»). То есть это не блокировка, а сбой извлечения — чинится на нашей стороне.
- Склейка русских и английских статей об одном событии.
- Транзакции в слое БД, свой заголовок события, `error.tsx`, метаданные страниц, аналитика.
- Перенос воркера на сервер с cron, локальная модель эмбеддингов, подбор порогов по вердиктам.

## Открытые вопросы и несогласия

1. **Срок хранения текстов** (фаза 8): предлагаю 14 дней, нужно ваше подтверждение.
2. **Противоречие со спецификацией.** CLAUDE.md §1 говорит: продукт «не переписывает чужие статьи другими
   словами». Текст одиночного события строится по одной статье и по сути является её пересказом.
   Вы решили, что тексты нужны всем событиям, — тогда §1 стоит переписать, а правовой риск
   («пользователю не нужно идти к источнику») оценить с юристом до публичного запуска. Я не юрист.
3. **Habr оставлен.** Отдельной обработки для него не делаю: при порядке «события с 2+ изданиями первыми»
   его посты естественно уходят в конец очереди. Ложное событие из 26 постов должна разобрать фаза 4.
4. **Неизвестные.** Учёт пакетных эмбеддингов в квоте, точность пакетной серой зоны, дневной лимит
   `gemini-3.5-flash-lite`. Все три проверяются экспериментом внутри фаз, с запасным вариантом.
