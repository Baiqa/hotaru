# Этап 1 — B-Cubed оценка (инструмент разметки + подсчёт метрик)

Цель: получить ground-truth разметку на ~250 статьях реального корпуса и посчитать
B-Cubed precision/recall для текущей кластеризации событий — это последний открытый
критерий готовности Этапа 1 из CLAUDE.md §5 ("B-Cubed precision и recall выше 0.8").

Результат **не блокирует Этап 2** автоматически — если метрики ниже 0.8, по
CLAUDE.md’s process мы документируем находки и решаем, калибровать веса сейчас или
отложить (уже есть 3 задокументированных кейса: Минфин over-merge, Habr NER-шум,
порог 0.40 для Dujuan) — это отдельная следующая подзадача, не часть этого плана.

Решения пользователя (зафиксированы):
- Хранение разметки: локальный файл в репо (не новая таблица Supabase).
- Выборка: случайная, но намеренно включает уже известные проблемные кластеры
  (крупные события, которые раньше были найдены руками — Минфин/Habr-26).
- Интерфейс разметки: статический HTML+JS + мини-локальный Python HTTP-сервер для
  автосохранения в файл, без сборки фронтенда.

## Шаги

1. **`worker/eval/sample.py`** — читает `events`/`event_articles`/`articles`/`sources`
   из Supabase (read-only, использует существующий `db.py`).
   - Эвристика "известные проблемные кластеры": все активные события с
     `member_count >= 5` включаются **целиком** (не по одной статье — чтобы в
     разметке группа была видна как полноценный кластер).
   - Остальное до ~250 статей добирается случайным отбором **на уровне событий**
     (берём случайное событие целиком, а не отдельные статьи) — чтобы в UI не
     было "обрубленных" групп из 2 статей при реальном размере события 5.
   - Пишет `worker/eval/sample_export.json`: список статей с `article_id, title,
     lead, source_name, published_at, predicted_event_id`, плюс отдельно список
     `predicted_event_id -> member article_ids` для группировки в UI.

2. **`worker/eval/labeling_tool/`** — `index.html` + `app.js`, без фреймворка.
   - Левая колонка: список групп (изначально = предсказанные события), с
     заголовком "Группа (pred: event <id>, n=<N>)".
   - Внутри группы — карточки статей (заголовок, источник, дата, лид).
   - Действия: переместить статью в другую группу (через dropdown на карточке),
     "новая группа" (выделить статью/статьи в отдельный кластер), "объединить
     группы" (две группы → одна). Это покрывает все 3 типа ошибок кластеризации:
     лишний merge, лишний split, неверная привязка.
   - Прогресс: счётчик "размечено групп / всего", чтобы было видно сколько
     осталось, и чтобы можно было прерваться и вернуться.
   - `labeling_tool/server.py` — `http.server` на localhost с одним POST-роутом,
     который атомарно перезаписывает `worker/eval/labels.json` при каждом
     изменении (без ручного "экспорта" после каждого клика). При старте страница
     подгружает текущий `labels.json`, если он уже существует (resume).
   - Запуск: `uv run python eval/labeling_tool/server.py` из `worker/` → открыть
     `http://localhost:8765` в браузере.

3. **`worker/eval/bcubed.py`** — считает метрики.
   - Ground truth: `labels.json` (article_id → ground_truth_cluster_id).
   - Predicted: текущие `events`/`event_articles` из БД для тех же article_id
     (резолвя `canonical_id` у merged-событий, как это уже делает `getEventById`
     на фронте).
   - Стандартная формула B-Cubed (per-item precision/recall, затем среднее).
   - Выводит: overall precision/recall/F1 + сравнение с порогом 0.8 из CLAUDE.md,
     и отдельно precision/recall **внутри** каждого заранее известного проблемного
     кластера (чтобы подтвердить/опровергнуть три прежние находки числами, а не
     интуицией).

## Что не входит в этот план

- Перекалибровка весов/порогов по результатам — отдельная следующая подзадача.
- Любые миграции БД — не нужны, всё read-only + локальный файл.
- Встраивание инструмента в прод (Next.js/`uv run hotaru-*`) — это одноразовый
  eval-инструмент, не часть пайплайна.

## Критерий готовности этого плана

- `labels.json` содержит ручную разметку на ~250 статьях (включая все известные
  проблемные крупные кластеры).
- `bcubed.py` выводит overall precision/recall + breakdown, без ошибок на полном
  сэмпле.
- Результат (числа) зафиксирован и сопоставлен с порогом 0.8 — дальше решение
  по Этапу 2 принимается пользователем на основе этих чисел, не до них.
