# Этап 5 — «одно событие, разные подачи»

## Контекст

Этап 5 — заявленный в CLAUDE.md §1 главный дифференциатор продукта: пользователь
видит не десять ссылок на одну новость, а картину того, кто что сообщил и в чём
источники не сходятся. Данные для этого уже накоплены Этапом 2 (`claim_groups`
с bucket confirmed/unique/disputed, `claim_group_members` с relation
confirms/contradicts) и растут сами по себе через cron, без участия фронта.
Это чистая фронтенд-задача: ни новой миграции, ни нового воркер-кода, ни
расхода Gemini-квоты не требуется.

Проверка реальных данных (не по спецификации): активных событий с ≥5
источниками — 12, из них с хоть какой-то группировкой фактов — 3, с реальным
disputed — 1 (Иран/Ормузский пролив, `982ea891-53c8-427e-bf63-c341061239ba`).
Это ожидаемо при текущем квотном узком месте, не повод откладывать — экран
должен корректно деградировать на тонких данных и сам наполнится по мере роста
покрытия.

**Пользователь решил:** барометр расхождения тона — отложить (нужна новая
LLM-экстракция тона, которой в проекте вообще нет, и это ещё одна нагрузка на
тот же дефицитный лимit, что group_claims/synthesize). Экран — отдельная
страница `/events/[id]/compare`, не секция на `/events/[id]`.

## Дизайнерское решение: три пункта CLAUDE.md — одна унифицированная матрица

CLAUDE.md перечисляет матрицу, подсветку противоречий и уникальные детали как
три отдельные вещи. Решено не строить три отдельных блока (это дублировало бы
одни и те же данные), а сделать **одну матрицу фактов×источников, где строка
раскрывается по клику** (тот же `<details>` паттерн, что в Этапе 2):
- confirmed-строка: ✓ у всех подтвердивших источников, раскрытие показывает
  общую формулировку факта + список подтвердивших.
- unique-строка: ✓ только у одного источника, раскрытие — «только {источник}
  упоминает, что {текст}».
- disputed-строка: ✓ у расходящихся источников + янтарная пометка «Расходится»
  (тот же цвет, что бейдж disputed в Этапе 2), раскрытие показывает **точную
  формулировку каждого источника отдельно** — это и есть «А сообщает X, Б
  сообщает Y», без отдельного блока-дубликата.

Выше матрицы — ряд карточек «заголовки рядом» (headline каждой статьи события,
не дедуплицированный по источнику — это сам по себе сигнал: разная подача
заголовка). Переиспользует уже загруженные `event.members` из `getEventById`,
без нового запроса.

## Файлы

**Новый `web/src/lib/comparison.ts`** (копирует конвенции `renders.ts`: свой
`UUID_RE`, `one<T>()`, проходит через `resolveActiveEventId`):

```ts
export type ComparisonMember = { sourceName: string; sourceUrl: string; text: string; evidence: string };
export type ComparisonFact = {
  groupId: string;
  bucket: "confirmed" | "unique" | "disputed";
  representativeText: string; // текст самого раннего claim в группе (joined_at)
  sourceNames: string[];      // уникальные источники группы, для колонок-чекбоксов
  members: ComparisonMember[]; // все claim'ы группы, для раскрытия
};
export type EventComparison = {
  sources: string[];          // все источники, у которых есть хоть один grouped claim в событии — колонки матрицы
  facts: ComparisonFact[];    // строки, order by claim_groups.created_at
};

export async function getEventComparison(id: string): Promise<EventComparison | null>
```

Один запрос: `claim_groups` события + embed `claim_group_members(relation,
joined_at, claims(text, evidence, articles(canonical_url, sources(name))))`,
`order("created_at")` на группах. Сборка в JS: группировка по `group_id`,
`representativeText` = claim с минимальным `joined_at`, `sources` = `[...new
Set(...)]` объединением всех members по всем группам. Нет групп или `sources`
< 2 → `null` (graceful "недостаточно данных", как `renders.ts` возвращает
`null` при отсутствии рендера).

**Новый `web/src/app/events/[id]/compare/page.tsx`** + `not-found.tsx` (тот же
`UUID_RE`+`notFound()` паттерн, что `events/[id]/page.tsx` и `articles/[id]`):
- Заголовки карточками (flex-wrap, zinc border), headline+источник+ссылка на
  `/articles/[id]` или прямо на `canonical_url` — как в текущем списке
  источников на `/events/[id]`.
- Матрица: `<table>` или CSS-grid — факты (строки) × источники (колонки),
  ячейка `✓`/`—`; disputed-строка — янтарный фон/метка. Строка целиком —
  `<summary>` в `<details>`, раскрытие — контент по правилу выше (confirmed/
  unique/disputed differ).
- Нет данных (`getEventComparison` вернул `null`) → `<p>` "Пока недостаточно
  сгруппированных фактов, чтобы сравнить подачи — заходите позже." вместо
  ошибки или пустой таблицы.
- `export const dynamic = "force-dynamic"` (как везде).

**Изменение `web/src/app/events/[id]/page.tsx`**: одна строка-ссылка
`Сравнить подачи →` на `/events/[id]/compare`, рядом с мета-строкой
(количество источников/обновлено). Показывается всегда (не скрывается по
условию) — страница назначения сама обрабатывает недостаток данных, как
принято для рендера на Этапе 2.

## Проверка

- `npm run build && npm run lint` в `web/` — чисто.
- В браузере: `/events/982ea891-53c8-427e-bf63-c341061239ba/compare` — реальное
  disputed-событие (Иран/Ормузский пролив, 4 источника) — матрица строится,
  disputed-строка про число танкеров (0.2 доли/5 танкеров в сутки) раскрывается
  с отдельной формулировкой Guardian и BBC.
- `/events/15462226-d17a-49b0-b9f2-5f6c277e823f/compare` — событие с 6
  источниками без disputed — confirmed-строки, без янтарных меток.
- Событие без группировки вообще (большинство из 930) → открыть `/compare` для
  произвольного такого id, убедиться в корректном "недостаточно данных",
  без 500-й.
- Ссылка "Сравнить подачи →" видна на `/events/[id]` для всех трёх кейсов.
