# План: Этап 1 → «Функция скоринга (4 сигнала) + отбор кандидатов»

Дата: 2026-09-27. Третья подзадача Этапа 1 (после "Сущностей" и "Эмбеддингов"), не весь
этап целиком. Явно НЕ входит в эту подзадачу (по словам пользователя — следующим шагом):
два порога, LLM для серой зоны, таблицы `events`/`event_articles`. Их тут не строим.

Раздел 3.3 CLAUDE.md — функция близости на уровне событий:

| Сигнал | Вес | Как считаю |
|---|---|---|
| Жаккар сущностей | 0.35 | По `article_entities` — уже есть из подзадачи "Сущности" |
| Числа и даты | 0.20 | Regex по title+lead+body, Жаккар по нормализованным токенам — см. ниже |
| Косинус эмбеддингов | 0.30 | По `articles.embedding` (title+lead) — уже есть из подзадачи "Эмбеддинги" |
| Близость по времени | 0.15 | exp(-ln2 · Δt_часы / 24) — полураспад 24ч, как указано в CLAUDE.md |

Веса — ровно те, что в CLAUDE.md. "Подбираются на размеченной выборке" — это когда
появятся `events` и B-Cubed-разметка, не раньше (тот же принцип, что и в прошлых
подзадачах).

**Важно про кандидатов:** сравниваем новую статью не с событиями (их пока нет и не
будет в этой подзадаче), а с другими **статьями** — это не заглушка, а то, что
буквально написано в разделе 3.3: "сравнивать статью не с общим центроидом кластера,
а с несколькими последними участниками". То есть построенная здесь функция — это
именно тот кирпич, который следующая подзадача (пороги + события) будет использовать
как есть, не переделывая.

## 1. Модуль `worker/src/hotaru_worker/scoring.py`

- `extract_number_date_tokens(text: str) -> set[str]` — regex по числам (в т.ч. с
  запятой как десятичным разделителем — нормализуем "16,5" и "16.5" к одному виду)
  и датам (годы, "15 сентября"/"September 15" и т.п.) из title+lead+body.
- `entity_jaccard(entities_a: set, entities_b: set) -> float` — |A∩B|/|A∪B|, 0 если
  оба множества пустые.
- `tokens_jaccard(...)` — та же формула, для чисел/дат.
- `time_decay(published_a, published_b) -> float` — exp(-ln2 · |Δt| в часах / 24).
- `score(candidate_row) -> float` — взвешенная сумма 4 сигналов по весам из таблицы
  выше. Косинус эмбеддингов достаём прямо из SQL-запроса кандидатов (pgvector уже
  считает `<=>` на этапе отбора, не пересчитываем в Python).

## 2. Отбор кандидатов

SQL-запрос: статьи, которые
- не сама статья,
- имеют `embedding is not null`,
- `published_at` в пределах N дней от целевой статьи (окно события — "часы-дни" по
  разделу 3.3, беру N=5 как разумный дефолт, потом можно подстроить на разметке),
- делят хотя бы одну сущность (join через `article_entities`),
- топ-50 по косинусной близости pgvector (`order by embedding <=> ... limit 50`).

Функция `find_candidates(conn, article_id) -> list[dict]` возвращает кандидатов с
уже посчитанным косинусом; `score_candidates(conn, article_id) -> list[(candidate, score)]`
досчитывает остальные 3 сигнала и сортирует по итоговому скору.

## 3. Без отдельной точки входа

В отличие от прошлых двух подзадач, здесь не пишем `uv run hotaru-...` — это не
шаг пайплайна, который пишет что-то в БД, а библиотека функций, которую использует
следующая подзадача (пороги + события). Проверяю напрямую вызовами функций.

## 4. Проверка перед «готово»

- На реальных данных: пара статей об одном сюжете (Китай/датацентры ИИ, тайфун Dujuan —
  те же примеры, что валидировали эмбеддинги) должна получить высокий итоговый скор;
  случайная пара — низкий. Явный разрыв между ними.
- Разбираю скор на сигналы (не только итог) хотя бы для одной пары — чтобы убедиться,
  что каждый сигнал по отдельности считается разумно, а не просто "в среднем сошлось".
- `find_candidates` реально уважает окно по времени и общую сущность (не возвращает
  статьи без общих сущностей или за пределами окна).
- Пустые множества сущностей/чисел не роняют функцию (нет ZeroDivisionError).
