# План: Этап 1 → «Два порога + LLM серой зоны + таблицы events/event_articles»

Дата: 2026-09-27. Четвёртая подзадача Этапа 1 (после "Сущностей", "Эмбеддингов",
"Скоринга"). Вне скоупа: фоновые merge/split задачи (следующая подзадача — именно
они компенсируют неидеальные склейки этой подзадачи, поэтому не страшно, если
инкрементальная обработка иногда ошибается), фронт-карточка события, сюжеты/event_links.

Решения этой сессии:
- **"related" от LLM трактуем как "different"** — на этом шаге всего два исхода
  (присоединить/новое событие), различие между related и different появится позже,
  на уровне сюжетов (Этап 4), которого пока нет.
- **Нижний порог — 0.40, не 0.45 из CLAUDE.md.** На реальной паре про тайфун Dujuan
  (точно одно событие) скор оказался 0.413 — ниже 0.45, то есть пара автоматически
  ушла бы в "новое событие", не дойдя до LLM. Разбор по сигналам (0.35·0.208 +
  0.20·0.0 + 0.30·0.882 + 0.15·0.5 = 0.413): сигнал "числа/даты" дал ровно 0 — фильтр
  коротких чисел (см. подзадачу "Скоринг") отбросил "4" из "4 killed" как шум, весь
  вес 0.20 потерян впустую на этой паре; Жаккар сущностей средний (0.208, вероятно
  анонс и факт-статья о том же шторме упоминают разные наборы сущностей); косинус
  (0.882) один держит почти весь скор. С порогом 0.40 пара уходит в серую зону и
  долетает до LLM — корректно. Не окончательная перекалибровка весов (та требует
  размеченной выборки, как и пишет CLAUDE.md), просто минимальная правка нижнего
  порога под конкретный доказанный случай false negative.

Модель для серой зоны: **`gemini-2.5-flash-lite`** — проверил напрямую через SDK
(`client.models.list()`) и официальный прайсинг: стабильная (не preview), бесплатный
тир для текста подтверждён, самый дешёвый платный фолбэк среди flash-lite вариантов.

## 1. Миграция БД

```sql
create table events (
  id uuid primary key default gen_random_uuid(),
  canonical_id uuid references events(id),  -- для будущего merge (null = сама каноническая)
  title text not null,                      -- пока = заголовок статьи-основателя события
  started_at timestamptz not null,
  updated_at timestamptz not null default now(),
  centroid vector(768),
  status text not null default 'active' check (status in ('active', 'merged')),
  created_at timestamptz not null default now()
);

create table event_articles (
  article_id uuid primary key references articles(id) on delete cascade,  -- статья в ровно 1 событии
  event_id uuid not null references events(id) on delete cascade,
  similarity_score double precision,  -- null для статьи-основателя (сравнивать было не с чем)
  joined_at timestamptz not null default now()
);
create index event_articles_event_id_idx on event_articles (event_id);

-- Раздел 3.3: "Ответы кешируются по паре id" — этой таблицы нет в разделе 4 CLAUDE.md,
-- добавляю как прагматичное расширение под явное требование кеша.
create table gray_zone_verdicts (
  article_a_id uuid not null references articles(id) on delete cascade,
  article_b_id uuid not null references articles(id) on delete cascade,
  verdict text not null check (verdict in ('same', 'related', 'different')),
  created_at timestamptz not null default now(),
  primary key (article_a_id, article_b_id)
  -- пара всегда хранится в порядке article_a_id < article_b_id (нормализация в коде)
);
```

Никакого нового столбца-флага на `articles` не завожу — "обработано" = "есть строка
в `event_articles`" (article_id — сам PK), тот же приём, что и в эмбеддингах.

## 2. Промпт серой зоны — `prompts/gray_zone_classify.txt`

По разделу 7 CLAUDE.md: "Промпты к моделям хранятся в отдельных файлах (prompts/),
а не в коде". Промпт: два заголовка+лида, просьба ответить строго одним словом
same/related/different. По возможности — structured output (enum) через
`response_schema` google-genai SDK вместо парсинга свободного текста; если модель
всё равно не впишется в три значения — трактую как `different` (безопасный дефолт:
лучше не склеить два разных события, чем ошибочно смешать факты о них).

## 3. Модуль `worker/src/hotaru_worker/clustering.py`

Алгоритм на статью (раздел 3.3 CLAUDE.md, инкрементально, одна статья за раз):

1. `scoring.score_candidates(conn, article_id)` → список кандидатов по убыванию скора.
2. Если кандидатов нет → новое событие.
3. Берём **лучшего** кандидата (топ-1, по буквальному тексту раздела 3.3 — "скор по
   каждому кандидату" → "решение по двум порогам", не перебор списка):
   - скор > 0.75 → присоединиться к событию кандидата
   - скор < 0.40 → новое событие
   - между → `gray_zone_verdicts` (кеш по паре id) → если нет, запрос к
     `gemini-2.5-flash-lite` → `same` присоединиться, `related`/`different` новое событие
4. "Присоединиться к событию кандидата": если у кандидата уже есть событие — берём
   его id. Если кандидат сам ещё не обработан (окно по времени симметричное, кандидат
   мог быть опубликован позже целевой статьи и ещё не дойти в очереди) — **создаю
   новое событие и сразу присоединяю к нему обе статьи** (кандидата и текущую), а не
   падаю и не жду. Это самовосстанавливающееся поведение, а не костыль: несовершенство
   такого порядка обработки — ровно то, что чинит будущая фоновая задача слияния.
5. `centroid` события — простое среднее эмбеддингов всех участников, пересчитывается
   при каждом присоединении (полный пересчёт по всем участникам, не инкрементально —
   при текущих объёмах дёшево, а раздел 3.3 explicitly говорит НЕ использовать
   centroid для решений о совпадении — только для показа/будущего merge).

## 4. Точка входа `hotaru-cluster-events`

По образцу прошлых подзадач: батчи с новым соединением на каждый (тот же урок про
пул Supabase), но **строго последовательно и в порядке `published_at`** (не просто
"необработанные" — порядок важен для корректности инкрементального алгоритма).
Берёт статьи, у которых есть и `embedding`, и извлечённые сущности
(`entities_extracted_at is not null`), но нет строки в `event_articles`.

## 5. Проверка перед «готово»

- Прогон на всех 548 статьях без падений.
- Пара про тайфун Dujuan (0.413, теперь в серой зоне с порогом 0.40) реально уходит
  на LLM и реально получает "same" → обе статьи в одном событии.
- Пара про Китай/датацентры (0.517, серая зона) — аналогично, LLM → "same" → одно
  событие.
- Идемпотентность: повторный прогон — 0 новых событий/присоединений.
- Кеш серой зоны реально работает: повторный вызов на той же паре не делает новый
  запрос к Gemini (проверяю по счётчику вызовов, не только по отсутствию ошибок).
- `centroid` действительно пересчитывается при присоединении (не остаётся эмбеддингом
  только основателя).
- Хотя бы один реальный случай реально уходит в серую зону и реально долетает до
  Gemini (не только теоретически проходимый code path) — уже обеспечено двумя
  пунктами выше.

## Вне скоупа
Фоновые merge/split, фронт-карточка события, сюжеты/event_links, B-Cubed-разметка
(нужна на этом же шаге в теории, но полноценная ручная разметка 200-300 статей —
отдельная работа, не блокирует техническую реализацию порогов). Полная перекалибровка
весов (0.35/0.20/0.30/0.15) — тоже требует разметки, не делаю её здесь, только
разовую точечную правку нижнего порога, обоснованную конкретным примером.
