# Этап 1, подзадача: фронт — карточка события со списком источников

Решения по вопросам пользователя (2026-10-06):
1. Главная (`/`) заменяется списком событий (не отдельный `/events`-роут рядом со старым списком статей).
2. Ссылка на каждый источник в событии ведёт на внутреннюю `/articles/[id]` (не на внешний сайт издания напрямую).
3. Список событий показывает все активные события, включая однo-статейные.
4. Сортировка — по `updated_at` убыванием (новые/активные события сверху).

## Почему без миграций

Схема `events`/`event_articles` (миграция `20260927150000_events.sql`) уже даёт всё нужное: `title`, `started_at`, `updated_at` (бампается триггером `set_updated_at` при любом UPDATE строки, включая `recompute_event_centroid` после присоединения/merge/split — то есть сортировка по `updated_at` реально отражает "последнюю активность", не просто дату создания), `status`, `canonical_id`. RLS на `events`/`event_articles` уже разрешает публичный SELECT. Задача чисто фронтовая.

## Важный краевой случай: смёрженные события

`db.merge_events()` (worker) помечает поглощённое событие `status='merged'`, выставляет его `canonical_id` на событие-победитель и переносит все его `event_articles` на победителя — то есть у самого поглощённого события `event_articles` становится пустым. CLAUDE.md §3.3 явно требует: "старые ссылки не должны умирать". Значит `getEventById`:
- если `status = 'merged'` — переходит по `canonical_id` к живому событию (с защитой от зацикливания, максимум несколько прыжков) и показывает его, а не 404 и не пустую карточку.

Это проверю на реальных данных — сегодняшний прогон `hotaru-merge-events` создал настоящие `status='merged'` строки в БД.

## Файлы

**Новый `web/src/lib/events.ts`** (по образцу `articles.ts`):
- `listEvents()`: `select` из `events` где `status = 'active'`, `order by updated_at desc`, `limit 30`, с вложенным `event_articles(articles(sources(name)))` — на выходе список событий с `{id, title, startedAt, updatedAt, sourceNames: string[], articleCount}` (имена источников — уникализированные).
- `getEventById(id)`: валидация UUID (как в `articles.ts`), подтягивает событие + все статьи-участники с их источником, title, lead, published_at, canonical_url (для ссылки на `/articles/[id]`, не напрямую на сайт издания). Следует по `canonical_id`, если событие `merged`. Возвращает `null`, если не найдено после резолва.

**`web/src/app/(list)/page.tsx`** — переписывается на `listEvents()`. Карточка: заголовок события → ссылка на `/events/[id]`, под ним список источников (имена через " · "), дата (`updatedAt`, через существующий `formatDate`).

**`web/src/app/(list)/loading.tsx`** — скелетон не меняется структурно (те же плейсхолдер-блоки подходят и для карточки события).

**Новый `web/src/app/events/[id]/page.tsx`** — заголовок события, даты started/updated, затем список статей-участников: источник + заголовок статьи + дата, каждая ссылкой на `/articles/[id]`. `export const dynamic = "force-dynamic"` (как везде, без этого следующие статьи от воркера не появятся без ребилда).

**Новый `web/src/app/events/[id]/not-found.tsx`** — по образцу `articles/[id]/not-found.tsx`, текст "Событие не найдено.", ссылка "← На главную" на `/`.

**Намеренно НЕ добавляю** `loading.tsx` для `events/[id]` — тот же баг, что уже найден и задокументирован для `articles/[id]`: Suspense-обёртка превращает `notFound()` в мягкий 200 вместо настоящего 404.

**`web/src/app/articles/[id]/page.tsx` и `not-found.tsx`** — небольшая правка текста ссылки назад: сейчас "← Ко всем статьям" ведёт на `/`, но там теперь события, а не статьи — текст меняю на "← На главную". Дополнительно добавляю ссылку "← К событию" (запрос `event_articles` по `article_id` → `event_id`), если у статьи есть событие.

## Проверка (перед "готово")

- `npm run build` и `npm run lint` — чисто.
- `npm run dev` + curl: `/` показывает карточки событий (не отдельные статьи), сортировка соответствует `updated_at` в БД (сверю напрямую через SQL).
- Событие с 1 источником и событие с несколькими источниками — оба рендерятся корректно на `/events/[id]`, ссылки на `/articles/[id]` работают.
- Найду в БД реальную строку `status='merged'` из сегодняшнего прогона merge — открою её `/events/<id>` и проверю, что показывается живое каноническое событие, а не 404/пустая страница.
- Невалидный id и несуществующий (но валидный по формату) UUID на `/events/[id]` → настоящий 404.
- `/articles/[id]` — ссылка "← К событию" ведёт на правильное событие.

Сообщу результаты проверки explicitly по каждому пункту, не просто "всё ок".
