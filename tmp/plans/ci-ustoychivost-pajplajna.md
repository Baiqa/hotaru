# План: устойчивость пайплайна на GitHub Actions

Дата: 2026-11-09. Статус: **ждёт одобрения, код не менялся**.

## Что установлено (проверено)

1. **Cron работает, но редко.** За ~20 ч на GitHub: collect 5 раз, llm 4 раза, maintenance-hourly 5 раз (вместо 40/50/20 по расписанию). GitHub троттлит `schedule` в публичных репо: примерно один запуск раз в 2–4 ч. Прежний вывод «cron не срабатывает» был неверным.
2. **Поток статей ~400–700 в сутки, а не ~40** (created_at: 7 ноября — 789, 8 ноября — 431 к 19:00 UTC). Расчёт «влезает в 4–8 минут» был неверным.
3. **Extract entities медленный не из-за spaCy.** Замер на 8 статьях: spaCy ≈ 0,35 с/статью. Остальное — запросы в Supabase: на каждое упоминание (~40 на статью) `find_entity_by_alias` ≈ 0,11 с, а при промахе `list_aliases` скачивает весь список (5929 строк ru/org, ≈ 0,73 с) и затем rapidfuzz (≈ 0,01 с). Это и даёт ~6 с/статью локально и ~12 с на раннере.
4. **Cluster events и Extract claims упираются в дневную квоту Gemini (500 запросов/сутки на gemini-3.1-flash-lite, одна на все шаги).** Локальный прогон кластеризации: 267 статей обработано, 210 пропущено, 70 минут ушло на ожидание. Ответ 429 содержит `retryDelay: 46331s` и `PerDayPerProjectPerModel` — ждать бессмысленно, а `gray_zone.classify` ждёт до 8 попыток (до ~10 мин на статью), и `cluster_events` не прерывает прогон при 429 посреди батча. `llm`-job по той же причине отменялся по таймауту 45 мин.
5. **`uv sync --frozen` иногда падает** (09:24, 09:53, 10:45 UTC 8 ноября), следующие шаги идут дальше в сломанном окружении (`if: !cancelled()`) и тоже падают. Причину не знаю: логи без входа в GitHub недоступны. Предположение: сбой скачивания (модели spaCy по URL с github.com). Это предположение, не факт.
6. Моя локальная кластеризация сожгла дневную квоту Gemini. Квота сбросится около 08:00 UTC; `llm`-запуск, идущий сейчас на GitHub, тоже будет получать 429.

## Предлагаемые изменения (по порядку приоритета)

### A. Быстрая обработка сущностей (главное)
- `entities.py`: кэш алиасов в памяти на время прогона — `list_aliases` один раз на (lang, type), дальше пополняется при `add_alias`; кэш точных совпадений `alias → entity_id`. Поведение результата не меняется (тот же порог 92, тот же WRatio).
- Ожидание: ~6–12 с → ~0,5–1 с на статью. Проверка: на одной и той же выборке из 30 статей сравнить результат до/после (набор `article_entities`) и время. Расхождения в результатах — стоп.

### B. Быстрый отказ при дневной квоте Gemini
- `gray_zone.classify`: если 429 содержит `PerDay` в `quotaId` (или `retryDelay` > 10 мин) — сразу `raise` без повторов (новый тип `DailyQuotaExceeded`).
- `cluster_events`: при `DailyQuotaExceeded` завершать прогон, а не пропускать статью. То же в `extract_claims` (проверю, как там устроено).
- Проверка: юнит-проверка с подставным ответом 429 (без обращения к реальному API) — функция выбрасывает исключение за <1 с.

### C. Groq как запасной провайдер для серой зоны кластеризации (заменяет прежний вариант «считать different»)
- Состояние на 2026-11-09 (проверено): `GROQ_API_KEY` есть в `worker/.env` (файл в .gitignore), пробный вызов `groq_client.call_json` вернул `{"ok":true}` за ~2 с. Код Groq-fallback (`groq_client.py`, `claim_grouping.py`, `synthesis.py`, `group_claims.py`, `synthesize.py`, `quota.py`) уже написан, **не закоммичен**, компилируется; он покрывает только `group_claims` и `synthesize` (см. tmp/plans/groq-fallback.md).
- Предлагается добавить тот же третий уровень в `gray_zone.classify` (ответ same/related/different → JSON `{"verdict": "..."}`), чтобы кластеризация не зависела от 500 запросов Gemini в сутки. Тогда при `DailyQuotaExceeded` (пункт B) `cluster_events` переключается на Groq, а не завершается.
- `extract_claims` (структурный JSON с фактами и `evidence`) пока не трогаем: он сложнее и качество на Groq нужно сначала проверить отдельно.
- Лимиты бесплатного тарифа Groq точно не знаю (в плане groq-fallback.md стояла оценка ~1000 запросов/сутки, она не проверена). Реальный лимит увидим по ответам 429/заголовкам при первых больших прогонах.
- Качество: Groq-вердикты нужно сверить с Gemini на выборке (≥30 пар серой зоны, согласие вердиктов), прежде чем включать в CI.

### E. Передача ключа Groq в GitHub Actions
- В `llm.yml` и `collect.yml` добавить `GROQ_API_KEY: ${{ secrets.GROQ_API_KEY }}` в `env`. Сейчас его там нет, поэтому на GitHub Groq не используется, даже если секрет добавлен. Сам секрет вы добавляете в Repository secrets самостоятельно (я ключи не трогаю). Я не могу проверить, добавлен ли он: прошу подтвердить.
- Перед пушем: проверка репозитория на секреты (публичный репо) и ваше подтверждение коммита. Незакоммиченные правки Groq лучше закоммитить отдельным коммитом до изменений A–D.

### D. Устойчивость workflow
- `uv sync --frozen` обернуть в 3 попытки с паузой; последующие шаги не запускать, если sync упал (убрать `!cancelled()` только для них или добавить `if: success() || ...` по шагам — уточню при правке).
- `timeout-minutes` оставить 30/45, но шаги теперь укладываются быстрее после A и B.
- Расписание: поскольку GitHub запускает реже, чем cron, не рассчитывать на «каждые 30 минут»; ожидание ≈ 1 прогон в 2–4 ч. Объём работы за прогон должен это выдерживать (по умолчанию так и будет после A).

## Критерии готовности
1. Локально: `extract_entities` на 30 статьях быстрее ≥5× с идентичным результатом.
2. Локально: `classify` на искусственном 429 PerDay падает сразу, `cluster_events` завершается без ожиданий.
3. На GitHub: один ручной запуск `collect` проходит все 4 шага за <30 мин (зелёный) либо останавливается на шаге Cluster events по квоте сообщением в логе.
4. Затем по одному ручному запуску `llm`, `maintenance-hourly`, `maintenance-daily`.

## Открытые вопросы к пользователю
- Добавлен ли `GROQ_API_KEY` в GitHub → Settings → Secrets (Repository secrets)? Без этого пункт E бесполезен.
- Пункт C: согласны ли вы распространить Groq на серую зону кластеризации (и коммитить уже написанный Groq-код отдельным коммитом)?
- Квота Gemini 500/день плюс неизвестная квота Groq всё равно может не покрыть ~500 статей/сутки вместе с фактами и синтезом. Если после A–E упрёмся, выбор: платный Gemini раньше срока или сократить поток (меньше источников / фильтр по свежести).
