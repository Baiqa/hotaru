# План: админ-страница /admin (воронка обработки, здоровье, качество, источники)

Решения пользователя (2026-11-17): страница `/admin` в `web/`; защита паролем из переменной окружения;
блоки — воронка обработки, здоровье шагов и квоты, качество кластеризации, по источникам и времени;
**только просмотр** (никаких кнопок запуска, интерфейс ничего не пишет в БД).

## Что обнаружено до плана (проверено в коде и БД)

1. **Служебные таблицы закрыты от анонима.** `pipeline_runs`, `gray_zone_verdicts`, `monitoring_checks`:
   RLS без политик + `revoke all from anon, authenticated`. Фронт ходит в БД только анонимным
   ключом, поэтому из текущего `web/src/lib/supabase.ts` эти таблицы не прочитать. Нужен серверный доступ.
2. **Service Worker кеширует страницы** (`web/public/sw.js`), **но по белому списку** `CACHEABLE_PAGE`
   (главная, events, stories, articles). `/admin` в него не входит, поэтому правка `sw.js` НЕ понадобилась
   (поправка к первой версии плана, проверено 2026-11-17). Дополнительно `/admin/*` отдаётся с `Cache-Control: no-store`.
3. **Данных о квотах Gemini/Groq в БД нет.** Остаток квоты можно узнать только живым запросом (тратит квоту).
   Поэтому блок «квоты» показывает оценку по журналу (`pipeline_runs.stats`: `gray_zone_requests`,
   `skipped_llm_unavailable`, число обработанных) и явно подписан «оценка», а не остаток.

## Архитектура

- **Доступ к данным: отдельная read-only роль в Postgres**, а не `service_role`.
  Миграция создаёт роль `admin_reader` (login, `select` только на нужные таблицы: articles, sources,
  events, event_articles, claims, claim_groups, renders, stories, pipeline_runs, gray_zone_verdicts,
  entities-таблицы только для счётчиков). Фронт подключается серверным кодом через `pg`
  (`ADMIN_DATABASE_URL`, пулер Supabase, session mode, порт 5432). Так утечка пароля/кода не даёт записи в БД,
  в отличие от service_role. Альтернатива (отвергнута): `SUPABASE_SERVICE_ROLE_KEY` в web — полный доступ на запись.
- **Агрегация в SQL, не в JS.** Один модуль `web/src/lib/admin-stats.ts`, запросы с `count(*) filter (...)`.
  Кеш `unstable_cache`/`revalidate` 60 с, чтобы обновление страницы не гоняло тяжёлые запросы.
- **Вход:** `/admin/login` (форма, server action). Пароль из `ADMIN_PASSWORD`; сравнение `timingSafeEqual`;
  успешный вход ставит httpOnly + Secure + SameSite=Strict cookie с HMAC-подписью (ключ — тот же пароль
  или отдельный `ADMIN_SESSION_SECRET`) и сроком 12 ч. Проверка cookie — на сервере в самом
  `/admin/layout.tsx` (не только в proxy). Если `ADMIN_PASSWORD` не задан — `/admin` отдаёт 404 (закрыто по умолчанию).
  Небольшая задержка при неверном пароле. `robots: noindex`, `Cache-Control: no-store`.
- **Без графических библиотек.** Свои SVG/CSS-компоненты (как в CLAUDE.md, раздел 2): столбцы воронки,
  стек по дням, спарклайны. Тёмная тема сайта, адаптивность до ширины телефона, без горизонтального скролла.

## Блоки страницы

1. **Воронка обработки** (всё в штуках и % от собранного): собрано → с полным текстом (ok/partial) →
   сущности извлечены → эмбеддинг есть → в событии → факты извлечены → факты с эмбеддингом → факты
   сгруппированы → у события есть сводка. Рядом «в очереди» на каждом шаге (сколько ждёт).
2. **Здоровье шагов и квоты:** по каждому шагу — последний запуск (статус, время, длительность,
   обработано), число запусков и сбоев за 24 ч, «зависшие» запуски (`running` старше N часов),
   промежуток с последнего успешного запуска. Оценка расхода LLM за сутки по шагам и флаг
   `skipped_llm_unavailable`. Сегодняшний пробел расписания (когда последний раз что-то работало).
3. **Качество кластеризации:** распределение размеров событий (1 / 2–4 / 5–9 / 10–19 / 20–39 / 40+),
   доля одиночных, **честная доля серой зоны по запускам** (`gray_zone_requests / processed` за 24 ч и по
   последним запускам — вместо приближения монитора), распределение вердиктов LLM (same/related/different),
   топ-10 крупнейших событий со ссылкой на `/events/[id]` (кандидаты в склейку).
4. **По источникам и времени:** приток статей по дням (стек по изданиям) за 14 дней, по источнику —
   всего, за 24 ч, доля partial (без текста), время последней статьи, подсветка «молчит > 24 ч».

## Файлы (предполагаемые)

- `supabase/migrations/<дата>_admin_reader_role.sql` — роль и гранты (применять только после твоего ОК:
  это изменение прав в БД).
- `web/src/lib/admin-db.ts`, `web/src/lib/admin-stats.ts`, `web/src/lib/admin-auth.ts`
- `web/src/app/admin/layout.tsx`, `page.tsx`, `login/page.tsx`, `login/actions.ts`
- `web/src/components/admin/*` — воронка, спарклайн, стек, таблицы
- `web/public/sw.js` — исключить `/admin` из кеша страниц
- `web/.env.local.example` — `ADMIN_PASSWORD`, `ADMIN_DATABASE_URL` (плейсхолдеры, без реальных значений)

## Критерии готовности (как проверяем)

- Без cookie `/admin` отдаёт редирект на логин, `/admin/login` не раскрывает ничего; при отсутствии `ADMIN_PASSWORD` — 404.
- Неверный пароль не ставит cookie; верный — ставит, и страница открывается; через 12 ч / после удаления cookie снова закрыта.
- Роль `admin_reader` **не может** писать: проверка `insert/update/delete` под этой ролью даёт ошибку.
- Цифры воронки сверены с прямыми SQL-запросами (совпадение числа в числе), а не друг с другом.
- Доля серой зоны на странице совпадает с ручным расчётом по `pipeline_runs`.
- `/admin` не попадает в кеш Service Worker (проверка в DevTools → Cache Storage).
- Страница читаема на ширине 375 px без горизонтального скролла; `npm run build` и `npm run lint` чистые.
- В репозиторий не попадают реальные пароли/строки подключения.

## Риски и допущения

- Деплой `web/` пока нигде не подтверждён (в репозитории нет `.vercel`). Если сайт публикуется, те же две переменные
  окружения нужно задать на хостинге; без них `/admin` закрыт (404).
- Пулер Supabase и serverless: каждое открытие страницы — несколько запросов; кеш на 60 с это сглаживает.
- Если пулер недоступен/проект на паузе (free-tier), страница покажет понятную ошибку, а не пустоту.
- Параллельно идёт локальная обработка воркера (кластеризация): страница только читает, конфликтов нет;
  цифры при этом будут меняться на глазах — это ожидаемо.

## Порядок работ (после твоего одобрения)

1. Миграция роли `admin_reader` + проверка прав. 2. Вход/выход и защита. 3. `admin-stats.ts` + сверка с SQL.
4. Компоненты и страница, по блоку за раз (воронка → шаги → качество → источники). 5. `sw.js`. 6. Проверка по критериям выше.
