## Файлы (новое, в worker/ — чтобы остаться частью воспроизводимого тулинга, не выкидыш в tmp/)

- `worker/eval/` — новая папка, попадает в git (сама разметка — ценные данные для будущей калибровки, не мусор).
- `worker/src/hotaru_worker/bcubed_sample.py`, entry point `hotaru-bcubed-sample`: строит выборку по рецепту выше, пишет `worker/eval/bcubed_sample.csv`.
  Колонки: `article_id, title, lead, source_name, published_at, predicted_group, true_event_label, reviewed`.
  `predicted_group` — короткий код (P001, P002…) вместо сырого UUID событий, чтобы в таблице было видно совпадения на глаз. Строки отсортированы по `(predicted_group, published_at)` — рядом видно, что сейчас склеено системой.
  `true_event_label` **предзаполняется значением predicted_group** (рабочая гипотеза = "система права, пока не исправлено") — вы правите только те строки, где не согласны, не 300 с нуля. `reviewed` = `FALSE` по умолчанию, выставляете `TRUE` по мере просмотра строки — так видно прогресс и какие строки реально посмотрены, а не просто проехали глазами.
- `worker/src/hotaru_worker/bcubed_score.py`, entry point `hotaru-bcubed-score`: читает тот же CSV **после** вашей разметки, считает B³ precision/recall/F1 по стандартной формуле (группировка по `predicted_group` vs `true_event_label`, только среди строк с `reviewed=TRUE`), отдельно считает долю двух типов ошибок (склеили разное / разорвали одинаковое) — как явно требует CLAUDE.md §5.
  Самопроверка перед тем, как отдать вам реальный файл: прогоняю на синтетическом кейсе (идентичная разметка true=predicted → precision=recall=1.0; намеренно испорченная разметка → метрики падают предсказуемо) — чтобы не отдать вам скрипт с ошибкой в самой формуле.
