# Калибровка кластеризации по результатам B-Cubed-разметки

Контекст: `worker/eval/` (sample.py, labeling_tool/, bcubed.py) дал реальную ground truth
на 250 статьях. B-Cubed precision 0.927 / recall 0.897 — порог CLAUDE.md §5 (0.8) уже
пройден. Калибровка ниже — не для прохождения порога, а чтобы закрыть три конкретных
найденных кейса доказательно, а не анекдотически.

Расследование (`event_merge.py`, `event_split.py`, `clustering.py`/`scoring.py` — все три
механизма проверены на живых данных) показало, что причины НЕ там, где их искали раньше:
не веса scoring.py, не NER-шум на Habr. Три находки ниже.

## Находка 1 — Habr-26 over-merge → `event_merge.py`

Все 25 сателлитов были отдельными events из одной статьи; incremental-join (`clustering.py`)
ни разу не дал score > 0.75 для пары внутри кластера (максимум 0.439), и LLM в gray-zone
13/16 раз сказала "different", 0 раз "same". Склеила их часовая `event_merge.py`
(`MERGE_THRESHOLD = 0.85` по чистому косинусу центроидов).

Проверка на 4 корректных крупных кластерах (Trump/CNN, Lavrov-Rubio, YouTube-AI,
Pezeshkian) показала тот же механизм работает ПРАВИЛЬНО там — но диапазоны косинуса
пересекаются (Habr: 0.70–0.88, корректные: 0.69–0.94). **Поднять порог косинуса нельзя**
— либо не уберёт Habr, либо сломает рабочие кластеры.

Чистый разделитель — сущности: у всех 4 корректных кластеров есть настоящие сущности,
общие для ≥половины статей (CNN, Trump, Лавров, Рубио...). У Habr — ноль таких сущностей
даже при 25 статьях.

**Фикс:** в `event_merge.py`, помимо `cosine_sim >= MERGE_THRESHOLD`, требовать хотя бы
одну "сущность большинства" (entity_id, встречающийся в ≥50% статей события), общую для
обоих событий-кандидатов на слияние.

- Новая функция `db.event_majority_entities(conn, event_id) -> set[str]`:
  ```sql
  select ae.entity_id
  from event_articles ea
  join article_entities ae on ae.article_id = ea.article_id
  where ea.event_id = %(event_id)s
  group by ae.entity_id
  having count(distinct ea.article_id) >= %(min_count)s  -- ceil(article_count/2)
  ```
- В `event_merge.py::run_once`, перед слиянием: пропускать кандидата, если
  `event_majority_entities(event) & event_majority_entities(candidate)` пусто.

## Находка 2 — false-split → `clustering.py` (top-1 → top-3)

Пример (Финляндия-БПЛА): правильная пара дала score 0.476 (gray-zone), но алгоритм
сравнивает только `scored[0]` — а им оказалась другая, несвязанная статья про Финляндию
со score 0.491 (обогнала на 0.015 из-за случайного совпадения общих сущностей). Верный
кандидат никогда не попадал на рассмотрение LLM.

**Фикс:** `cluster_article()` в `clustering.py` пробует до 3 лучших кандидатов по очереди
(`scored[:3]`), применяя ту же логику auto-join / auto-reject / gray-zone к каждому, и
останавливается на первом, для которого `should_join = True`. Новое событие создаётся
только если все до 3 кандидатов дали `False`.

Побочный эффект: до ×3 вызовов Gemini в gray-zone на статью (сейчас максимум 1) — дёшево
на free-tier, осознанно принято.

## Находка 3 — граничные случаи → `clustering.py::LOWER_THRESHOLD`

ДТ-экспорт (0.388) и резолюция ООН (0.398) — чуть ниже текущего порога 0.40, тот же
паттерн, что чинили раньше для Dujuan (0.45→0.40).

**Фикс:** `LOWER_THRESHOLD = 0.40` → `0.38`.

**ИСПРАВЛЕНИЕ после реализации:** первичная проверка смотрела только на изолированный
score пары, не на реальный ранг через `score_candidates()`. Перепроверка показала: верная
пара для ДТ-экспорта — ранг **#19** среди реальных кандидатов (не #1), для резолюции ООН —
ранг **#17**. В обоих случаях первые 16-18 кандидатов обгоняют верную пару за счёт частых
сущностей (США, МИД, Белый Дом, Россия — встречаются в десятках несвязанных статей
корпуса). `CANDIDATE_TRIES=3` из находки 2 **не достаёт** до них — это другая, более
глубокая проблема (нужно IDF-подобное взвешивание сущностей по частоте в корпусе, а не
точечная правка). По решению пользователя — **оставлено как документированный открытый
лимит**, не дорабатывается в этом раунде калибровки. Порог 0.38 всё равно оставлен (чинит
находку 2 класс случаев типа Финляндии, где верная пара уже в топе по рангу).

## Не трогаем

- Веса `scoring.py` (WEIGHT_ENTITY_JACCARD/TOKENS_JACCARD/COSINE/TIME_DECAY) — без
  доказанной необходимости, риск переобучиться под 250-статейную выборку.
- NER-экстракция (`entities.py`, `extract_entities.py`) — хотя качество реально плохое на
  Habr (829 "сущностей" на 26 статей, по факту разметка на entity_jaccard никогда не была
  тем, что склеило Habr — Jaccard оставался почти нулевым из-за больших зашумлённых
  множеств).
- `event_split.py` (SPLIT_SIMILARITY_THRESHOLD = 0.65) — проверил, свидетельств проблем не
  нашёл.
- Живую БД (489 существующих events) — только код; новые пороги/проверки применяются к
  будущим статьям. Полный re-cluster всего корпуса — отдельное решение, не сейчас.

## Критерий готовности

- Юнит-проверка на уже найденных кейсах: пересчитать score_pair/merge-условие для всех
  3 находок с новым кодом и убедиться, что решение меняется в правильную сторону
  (Habr-пары больше не проходят merge-gate; Финляндия-пара становится кандидатом #1 или
  хотя бы входит в топ-3 и успешно join; ДТ-экспорт/ООН переходят в gray-zone).
- Не запускать повторно `bcubed.py` против живой БД (код не трогает существующие events) —
  проверка только на уровне функций, не на уровне пересчёта всего корпуса.
