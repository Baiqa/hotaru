# ADR-0002: PostgreSQL + pgvector на Supabase, эмбеддинги `gemini-embedding-2` (768)

**Статус:** Принято
**Дата:** 2026-09 (стек, спецификация §2); 2026-09-27 (эмбеддинги)
**Принимал:** владелец проекта

## Контекст

Нужны реляционные связи (статьи, события, факты, сюжеты) и векторный поиск (кластеризация, группировка фактов). Бюджета на
платные сервисы нет ([ADR-0008](0008-besplatnye-llm-i-fallback.md)).

## Решение

1. **Хранилище:** PostgreSQL с расширением `pgvector` в Supabase (бесплатный тариф). Реляционные данные и векторы в одном месте.
2. **Эмбеддинги:** Google Gemini Embedding API, модель `gemini-embedding-2`, размерность **768**, косинусная метрика.
   Эмбеддинг считается по заголовку и лиду статьи, не по всему тексту (§3.3 спецификации).
3. **Индексы:** HNSW с `vector_cosine_ops` на `articles.embedding` и `claims.embedding`.

## Рассмотренные варианты

| Вариант | Оценка |
|---|---|
| Postgres + pgvector (Supabase) | Выбран: связи и векторы вместе, бесплатный тариф |
| OpenRouter как провайдер эмбеддингов и LLM | Отвергнут 2026-09-27: у Google есть бесплатный тир и для чат-моделей, один провайдер вместо двух |
| Отдельная векторная БД | В источниках не рассматривалась |

Почему 768, а не 128/1536/3072: источник фиксирует только, что 768 — «один из рекомендуемых Google вариантов, компактный», а
`gemini-embedding-2` сам нормализует усечённые векторы. Измерения качества при разных размерностях не проводились.

## Последствия

- Проще: один источник правды, SQL-запросы по связям и по близости.
- Сложнее: размерность зашита в схему (`vector(768)` в пяти колонках: `articles.embedding`, `claims.embedding`, `events.centroid`,
  `claim_groups.centroid`, `stories.centroid`). Смена модели или размерности означает пересчёт всех эмбеддингов и миграцию колонок.
- Квота эмбеддингов бесплатного тарифа (около 1000 запросов в сутки) считается отдельно от чатовой и при потоке около 1100
  новых статей в сутки стала узким местом ([ADR-0009](0009-byudzhet-llm-ocheredi.md)).
- Индекс `claims_embedding_hnsw_idx` (около 22 МБ) по плану P0 (фаза 8) не используется кодом, его предложено удалить; решение не принято.
- Лимит размера БД бесплатного тарифа Supabase отдельно отслеживается в плане P0 (фазы 8–9).
