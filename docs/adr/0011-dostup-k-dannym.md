# ADR-0011: Доступ к данным: RLS, колонки, отдельная роль для `/admin`

**Статус:** Принято
**Дата:** 2026-11-12 (колонки), 2026-11-17 (роль `admin_reader`), 2026-11-18 (отзыв грантов)
**Принимал:** владелец проекта

Полное описание прав: [docs/rbac.md](../rbac.md). Здесь только решения и их причины.

## Контекст

Браузер ходит в БД анонимным ключом, поэтому всё, что доступно роли `anon`, публично. Аудит 2026-11-11 показал, что политика «публичное чтение»
(RLS ограничивает строки, а не колонки) вместе с грантом Supabase по умолчанию отдавала анониму все колонки `articles`, включая `body` (получено
8109 символов чужого текста). Это нарушало правило §3.1: полный текст только для внутренней обработки. Отдельно: странице `/admin` нужен доступ к
служебным таблицам (`pipeline_runs`, `gray_zone_verdicts`), закрытым от анонима.

## Решение

1. **RLS включён на всех таблицах** `public`; публичный контент читается политиками «publicly readable».
2. **Колонки закрываются грантами:** у `articles`, `claims`, `events`, `claim_groups`, `stories` табличный `SELECT` отозван и выдан явный список колонок
   (нет `body`, `embedding`, `content_hash`, `centroid`).
3. **У `anon` и `authenticated` только `SELECT`:** запись и `TRUNCATE`, `REFERENCES`, `TRIGGER`, `MAINTAIN` отозваны миграциями 2026-11-18, чтобы запись не
   держалась на одном слое RLS.
4. **Админка с отдельной ролью:** `/admin` защищена паролем из переменной окружения, закрыта по умолчанию (404 без настройки) и читает БД ролью
   `admin_reader` (только `SELECT` по перечисленным колонкам, транзакции `read only`, таймаут 15 с, до 5 соединений), а не `service_role`.
5. Воркер подключается напрямую владельцем таблиц (`DATABASE_URL`, роль `postgres`), `service_role` не используется нигде.

## Рассмотренные варианты

| Вариант | Оценка |
|---|---|
| Ключ `service_role` в серверном коде `web/` для админки | Отвергнут: утечка даёт полный доступ на запись |
| Отдельная read-only роль `admin_reader` | Выбран |
| Ограничение только RLS | Недостаточно: RLS не скрывает колонки (`body`) |
| Данные квот Gemini/Groq на странице админки | Остаток квоты в БД не хранится; блок честно подписан «оценка по журналу запусков» |

## Последствия

- Новые колонки перечисленных таблиц нужно выдавать анону явно миграцией, иначе фронт их не увидит.
- Открытые риски (подробности в `docs/rbac.md`): воркер работает от `postgres` (утечка `DATABASE_URL` даёт полный доступ); один общий пароль админа без
  журнала входов; сертификат пулера Supabase при подключении `admin_reader` не проверяется; не проверено, включена ли регистрация в Supabase Auth.
- Права по умолчанию для таблиц, создаваемых ролью `supabase_admin` (например, из панели), не менялись; таблицы нужно создавать миграциями.
