# Новостное приложение с визуализацией — спецификация

Рабочий документ. Кладётся в корень репозитория, используется как контекст для Claude в VSCode.

---

## 1. Что это за продукт

Новостное приложение, которое не пересказывает статьи, а **собирает событие из нескольких источников** и показывает его как структуру: факты с атрибуцией, числа в историческом контексте, таймлайн сюжета, расхождения между изданиями.

Ключевое отличие от агрегаторов: пользователь видит не десять ссылок на одну новость, а одну картину события с пометкой, кто что сообщил и в чём источники не сходятся.

**Чего продукт сознательно не делает:** не переписывает чужие статьи другими словами, не показывает полный текст оригиналов, не выдаёт прогнозы и оценки от своего имени.

---

## 2. Платформа и стек

### Решение: web-first PWA, Android-обёртка через Capacitor на поздних этапах

| Слой | Выбор | Почему |
|---|---|---|
| Фронт | Next.js (App Router) + TypeScript | SSR для быстрой первой отрисовки, один код на веб и мобильный |
| Стили | Tailwind CSS | Скорость, консистентность |
| Визуализация | D3 (расчёты) + собственные SVG-компоненты; Recharts/visx для простых графиков | Полный контроль над графом и таймлайном |
| БД | PostgreSQL + расширение `pgvector` | Реляционные связи + векторный поиск в одном месте |
| Сбор данных | Python-воркер отдельно от фронта | Парсинг не помещается в serverless-лимиты |
| Очередь/крон | Крон-задачи воркера | Достаточно на старте |
| Android | Capacitor-обёртка над PWA | Push, шаринг, оффлайн без переписывания |

### Что обязательно, чтобы PWA не ощущалась как сайт

- Кеш последних сюжетов для оффлайн-чтения (Service Worker).
- Свои переходы между экранами, жест «назад».
- Скелетоны вместо спиннеров.
- Учёт safe area на устройствах с вырезом.
- Push-уведомления только через Capacitor-сборку (в вебе — опционально).

### Разделение на два процесса

```
[Python-воркер]  →  [PostgreSQL]  ←  [Next.js]
 сбор, извлечение,     хранение       чтение, рендер
 кластеризация,                       визуализация
 генерация текстов
```

Фронт **никогда не ходит в LLM и не парсит сайты**. Он только читает готовые данные. Это делает приложение быстрым и предсказуемым.

## 3. Пайплайн обработки

```
1. Сбор          источники → сырые статьи
2. Извлечение    статья → текст, сущности, факты, числа
3. Кластеризация статьи → события → сюжеты
4. Синтез        факты события → текст с атрибуцией
5. Обогащение    числа → исторические ряды → графики
6. Публикация    всё вышеперечисленное → БД → фронт
```

### 3.1. Сбор — лестница методов

Каждый следующий уровень включается, только если предыдущий не справился. У источника в конфиге поле `fetch_method`.

| Уровень | Инструмент | Когда |
|---|---|---|
| 1 | `feedparser` (RSS/Atom/sitemap) | По умолчанию. Должен покрывать 70–80% потока |
| 2 | `httpx` + `trafilatura` | Нет ленты или в ленте только анонс |
| 3 | `curl_cffi` | Сайт блокирует обычные запросы по TLS-отпечатку |
| 4 | `patchright` | Текст рендерится через JS |
| 5 | анти-детект браузер | **Не реализуем.** Сигнал, что сайт не хочет быть спарсенным |

**Правила вежливости (обязательны):**
- Соблюдать `robots.txt`.
- Задержка между запросами к одному домену, не меньше 1–2 сек.
- Условные запросы: `ETag` / `If-Modified-Since`.
- Честный User-Agent с контактом.
- Нормализация URL: убрать UTM-метки, взять `canonical`.

**Авторские права:** полный текст хранится только для внутренней обработки. Пользователю показывается свой синтез, цитаты не длиннее одного предложения, всегда со ссылкой на оригинал и названием издания.

### 3.2. Извлечение фактов

Каждая статья обрабатывается **отдельно**. Модель возвращает не текст, а структуру:

```json
{
  "claims": [
    {
      "text": "Нацбанк сохранил базовую ставку на уровне 16,5%",
      "type": "fact | statement | estimate",
      "evidence": "точная фраза из исходного текста",
      "entities": ["Нацбанк РК"],
      "numbers": [
        {"value": 16.5, "unit": "%", "label": "базовая ставка", "period": "2026-09"}
      ]
    }
  ]
}
```

**Жёсткое правило:** если `evidence` пустой или не находится в исходном тексте — факт отбрасывается. Это главный барьер против галлюцинаций.

Результат кешируется по хешу текста статьи: повторно та же статья не обрабатывается.

### 3.3. Кластеризация — два уровня

Это ключевое архитектурное решение. Один порог не может одновременно быть строгим и мягким.

| | **Событие** | **Сюжет** |
|---|---|---|
| Что это | Один факт реальности, о котором написали N изданий | Цепочка событий: решение → реакция → последствие |
| Окно | Часы–дни | Недели–месяцы |
| Порог | Высокий (одно и то же) | Низкий (связано) |
| Что показывает | Разные подачи, сверка фактов | Таймлайн, граф связей |

**Функция близости (для уровня событий):**

| Сигнал | Вес | Комментарий |
|---|---|---|
| Пересечение сущностей (Жаккар) | 0.35 | По нормализованным именам |
| Совпадение чисел и дат | 0.20 | Сильный и дешёвый сигнал |
| Косинус эмбеддингов | 0.30 | Считать по **заголовку + лиду**, не по всему тексту |
| Близость по времени | 0.15 | Экспоненциальное затухание, полураспад ~24ч |

Веса подбираются на размеченной выборке.

**Алгоритм (инкрементальный, не батчевый):**

1. Пришла статья.
2. Отбор кандидатов: топ-50 через `pgvector`, но **только** среди статей за последние N дней и делящих хотя бы одну сущность.
3. Скор по каждому кандидату.
4. Решение по двум порогам:
   - `> 0.75` → присоединить к событию
   - `< 0.45` → создать новое событие
   - между → **отдать на разбор LLM** (два заголовка и лида, ответ строго `same | related | different`)

Серая зона — примерно 10% потока, поэтому обращения к модели дёшевы. Ответы кешируются по паре id.

**Нормализация сущностей обязательна.** «Нацбанк», «НБ РК», «Национальный банк Казахстана» — одна запись. Нужна таблица алиасов + приведение к именительному падежу.

**Три механизма поддержки качества:**

- **Дрейф.** Сравнивать статью не с общим центроидом кластера, а с несколькими последними участниками. Плюс жёсткий лимит на длину окна события.
- **Слияние.** Фоновая задача раз в час ищет пары близких событий и объединяет. Поэтому у события должен быть `canonical_id` — старые ссылки не должны умирать.
- **Разделение.** Раз в сутки проверять внутреннюю связность кластера и резать, если он распался на две плотные группы.

### 3.4. Синтез текста

Модель, которая пишет текст, **не видит исходные статьи**. Только список фактов события.

Факты предварительно схлопываются и делятся на три корзины:
- подтверждённые несколькими источниками (у каждого счётчик),
- упомянутые только одним,
- противоречащие друг другу.

**Пост-проверка сгенерированного текста:**
1. Каждое предложение ссылается на `claim_id`. Нет ссылки → предложение удаляется.
2. Каждое число в тексте есть среди фактов. Нет → вся генерация отклоняется, повтор.
3. Ни одно предложение не совпадает дословно с оригиналом длиннее 8 слов (проверка по шинглам).

**Форматы вывода** — собираются из одного набора фактов разными промптами:
- сводка на 30 секунд,
- полный разбор,
- запись в таймлайн сюжета,
- «что нового с прошлого раза».

**Инкрементальность:** новая статья в существующем событии не запускает перегенерацию всего. Добавляются новые факты, обновляются только затронутые блоки.

**Языки:** источники на русском, казахском и английском. Факты нормализуются в один язык на этапе извлечения, иначе дедупликация не работает.

### 3.5. Числа и графики

Число из текста — это только якорь. График становится полезным, когда даёт контекст: исторический ряд, на котором текущая точка подсвечена.

Источники рядов: Нацбанк РК, Бюро нацстатистики, World Bank, FRED.

**Правила:**
- График рисуется только по числу, у которого есть `evidence` из текста.
- Тип графика выбирается по правилу, не моделью: изменение во времени → линия; сравнение → столбцы; доля → одна полоса.
- Круговые диаграммы не используются.
- По нажатию на любое число или точку → исходное предложение + источник.

## 4. Модель данных (черновик)

```
sources            издания: name, base_url, fetch_method, rss_url, lang, robots_checked_at
articles           url, canonical_url, source_id, title, lead, body, published_at,
                   content_hash, embedding vector, fetch_status
entities           canonical_name, type (person|org|place), external_id
entity_aliases     entity_id, alias, lang
article_entities   article_id, entity_id, mention_count
claims             article_id, text, type, evidence, embedding vector
claim_numbers      claim_id, value, unit, label, period
events             canonical_id, title, started_at, updated_at, centroid vector, status
event_articles     event_id, article_id, similarity_score, joined_at
stories            title, slug, started_at, updated_at, status
story_events       story_id, event_id, position
event_links        from_event_id, to_event_id, type, confidence, evidence
                   type: continuation | reaction | refutation | consequence
renders            event_id | story_id, format, lang, body, model, created_at
render_claims      render_id, sentence_index, claim_id
metric_series      key, label, unit, source_name, source_url
metric_points      series_id, period, value
```

**Пояснения:**
- `canonical_id` у события нужен для слияний: старый id остаётся и ведёт на новый.
- `event_links.evidence` — фраза, на которой построена связь. Без неё связь не показывается.
- `render_claims` — то, что делает возможной проверку «каждое предложение имеет источник».

## 5. Этапы разработки

Каждый этап заканчивается работающим состоянием. Не начинать следующий, пока критерии готовности не выполнены.

### Этап 0 — Скелет

**Цель:** статьи собираются и видны в приложении.

- Схема БД: `sources`, `articles`.
- Воркер: сбор по RSS для 5–10 источников, `trafilatura` для полного текста.
- Нормализация URL, дедуп по `canonical_url` и `content_hash`.
- Next.js: список статей, страница статьи (заголовок, лид, ссылка на оригинал).
- Крон раз в 30 минут.

**Готово, когда:** сутки непрерывной работы без падений, дубликатов по URL нет.

### Этап 1 — События

**Цель:** десять статей об одном событии схлопываются в одну карточку.

- Сущности: извлечение, таблица алиасов, нормализация.
- Эмбеддинги заголовка и лида, индекс `pgvector`.
- Функция скоринга (4 сигнала) + отбор кандидатов.
- Два порога + LLM для серой зоны.
- Таблицы `events`, `event_articles`.
- Фоновые задачи: слияние (раз в час), разделение (раз в сутки).
- Фронт: карточка события со списком источников.

**Готово, когда:** на размеченной выборке из 200–300 статей B-Cubed precision и recall выше 0.8. Отдельно отслеживаются два типа ошибок: склеили разное и разорвали одинаковое — они лечатся разными параметрами.

**Злые случаи для проверки:** два одинаковых заседания в разные даты; компании-тёзки; длинный сюжет с постепенным смещением темы.

### Этап 2 — Факты и синтез

**Цель:** у события есть свой текст, а не чужие заголовки.

- Извлечение фактов с `evidence`, кеш по хешу.
- Схлопывание фактов, три корзины (подтверждено / уникально / спорно).
- Генерация: сводка 30 секунд + полный разбор.
- Пост-проверка: ссылки на факты, числа, шинглы.
- `renders`, `render_claims`.
- Фронт: текст события, по нажатию на предложение — источник.

**Готово, когда:** нет ни одного предложения без `claim_id`; нет ни одного числа вне фактов; нет совпадений с оригиналом длиннее 8 слов.

### Этап 3 — Числа и графики

**Цель:** цифры в тексте становятся графиками с контекстом.

- `claim_numbers` из этапа 2.
- Загрузка исторических рядов, `metric_series` / `metric_points`.
- Сопоставление числа из текста с рядом.
- SVG-компоненты: линия, столбцы, полоса.
- «Откуда цифра?» — исходное предложение + источник по нажатию.

**Готово, когда:** график не отображается, если число не подтверждено текстом; каждый график кликабелен до первоисточника.

### Этап 4 — Сюжеты и таймлайн

**Цель:** видно развитие истории, а не отдельные события.

- Привязка события к сюжету (мягкие пороги, широкое окно).
- `event_links` с типами и `evidence`.
- Таймлайн в стиле схемы метро: время слева направо, ветки сюжета — линии, пересечения — точки.
- «Что нового с прошлого раза»: диф по фактам с момента последнего визита.

**Готово, когда:** сюжет из 20+ событий читается на экране телефона без горизонтального скролла.

### Этап 5 — Расхождения и подачи

**Цель:** самая отличительная функция продукта.

- Экран «одно событие — разные подачи»: заголовки изданий рядом, матрица «какой факт кто упомянул».
- Подсветка противоречий: «А сообщает X, Б сообщает Y».
- Уникальные детали: «только Б упоминает, что…».
- Барометр расхождений: не среднее настроение, а разброс тона между изданиями по одному событию.

**Готово, когда:** для события с 5+ источниками матрица заполняется автоматически и в ней нет пустых строк-артефактов.

### Этап 6 — Полный граф и персонализация

- Силовой граф связей как режим «исследовать» (не по умолчанию).
- Подписка на сущность, уведомления о новом в сюжете.
- Календарь запланированных событий по сюжету (только факты, без прогнозов).
- Скроллителлинг для главной истории дня.
- Capacitor-сборка под Android, push.

## 6. Мониторинг

Парсеры ломаются тихо: сайт меняет вёрстку, и источник начинает отдавать пустоту.

Проверки, которые должны работать постоянно:
- источник за 24 часа дал 0 статей → алерт;
- средняя длина текста по источнику упала более чем вдвое → алерт;
- доля отклонённых генераций выше 10% → алерт;
- доля серой зоны в кластеризации выше 25% → пороги съехали.

## 7. Порядок работы с Claude в VSCode

1. Этот файл лежит в корне репозитория и указывается как контекст.
2. Задачи ставятся **по одному разделу этапа**, а не «сделай этап целиком».
3. Для каждой задачи формулируется критерий готовности из раздела 5 — он проверяем.
4. Схема БД меняется только миграциями, а не правкой таблиц вручную.
5. Промпты к моделям хранятся в отдельных файлах (`prompts/`), а не в коде — их придётся часто править.
